Tailscale Widget — How it works

tailscale-widget is a small home-screen widget for the official com.tailscale.ipn Android app. It lets you connect/disconnect the VPN, jump to Tailscale settings (account switcher entry), and shows status — without reimplementing Tailscale.

Source: github.com/ajinkyajacob/tailscale-widget

High-level architecture

Widget lifecycle & actions

TailscaleWidgetProvider receives widget updates and tap intents (toggle/refresh), requests connection changes, and reconciles UI until the VPN state matches.

Rendering

WidgetRenderer resolves inputs into an explicit WidgetState and builds RemoteViews (status, dot, buttons, intents) for the widget.

Tailscale integration

TailscaleController is the only boundary to Tailscale/system: install check, VPN-active heuristic (TRANSPORT_VPN), and IPN broadcasts (CONNECT_VPN/DISCONNECT_VPN).

Account read & setup

AccountReaderService (accessibility, Tailscale window only) reads/caches the signed-in login and can drive the switch flow; SetupActivity onboards enabling it; AccountStore persists state.

Explicit state machines

The app’s behavior is now modeled with explicit states/enums instead of scattered flag branches.

1) Widget display state — WidgetState

Resolved in WidgetRenderer.resolveState(installed, vpnActive, pendingConnect):

NOT_INSTALLED  if !installed
CONNECTING     if pendingConnect == true
DISCONNECTING  if pendingConnect == false
CONNECTED      if pendingConnect == null && vpnActive
DISCONNECTED   if pendingConnect == null && !vpnActive

Transition driver: pendingConnect (Boolean overlay) → observed VPN state (TRANSPORT_VPN)

2) Toggle/reconcile flow — provider

idle/observed
  └─ tap toggle → desiredActive = !isVpnActive()
       └─ requestConnection(desiredActive) + render(pending=desiredActive)
            └─ reconciling: poll every 300 ms until vpnActive == desiredActive or 7 s timeout
                 └─ settled: render(pending=null, observed state)

Implemented in TailscaleWidgetProvider.handleToggle (optimistic UI held until the tunnel actually flips, to avoid flicker).

3) Account reader phases — AccountReaderService.ReaderPhase

SWITCH_PENDING      (scan 400 ms) → drive switcher / open account card
        │ success → clear switch, cache account, refresh widgets, enter settle
        ▼
POST_SWITCH_SETTLE  (guard ~3 s)  → ignore observations while UI settles
        │ timeout
        ▼
IDLE_OBSERVE       (scan 1000 ms) → read login-like email and cache on change
  • Card-click cooldown: ~800 ms (avoid repeated clicks while opening switcher).
  • Post-switch delayed widget refresh: ~2.5 s.
  • Only Tailscale’s window is observed (accessibility config scoped to com.tailscale.ipn).

4) Switch request window — AccountStore.SwitchRequestState

NONE --requestSwitch()--> PENDING (time-bounded, ~15 s)
 PENDING --clearSwitch() or expiry--> NONE

getSwitchRequestState() centralizes expiry/cleanup; the reader consults it to enter SWITCH_PENDING.

What is intentionally not a local “truth”

  • VPN state is heuristic: Android exposes an active VPN transport, not ownership. It’s treated as evidence (accurate in single-VPN practice) — see TailscaleController.isVpnActive.
  • No profile-switch API: Tailscale doesn’t expose account switching; the widget deep-links to Settings and (optionally) uses accessibility to read/assist — constrained by Tailscale’s UI.
  • Broadcast contract: connect/disconnect uses Tailscale’s own receiver actions; future Tailscale releases could change them.

Build, test, CI

Local build & tests:

./gradlew :app:testDebugUnitTest
./gradlew :app:assembleDebug

GitHub Actions (.github/workflows/android-ci.yml) runs unit tests and assembles the debug APK on pushes/PRs to main; (.github/workflows/pages.yml) deploys this docs/ site to GitHub Pages.
